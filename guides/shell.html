Guide 4 of 7 · Opening a terminal

What happens when you open a terminal

Between the window appearing and the prompt blinking, zsh reads four files in a fixed order. It takes about 145 milliseconds. Here is every step.

Four files, always in this order

zsh decides which files to read by asking two questions. Is this a login shell, the first one of a session? Is it interactive, with a person typing? A new Terminal window is both, so it reads all four.

In plain words

Think of opening a shop in the morning. Someone unlocks the door and switches on the lights (.zshenv). Someone sets out the stock (.zprofile). Someone arranges the counter the way the shopkeeper likes it (.zshrc). Then the cleaner tidies up out the back while the first customer is already being served (.zlogin).

Sitting on top of another setup

On some Macs a separate tool installs its own ~/.zprofile and ~/.zshrc, and rewrites them now and then. Editing those files would be pointless, because the edits would be wiped. Replacing them would break whatever that tool set up.

So this repository does neither. Its own startup files live in config/zsh, and each one begins by loading the file of the same name from the home folder, if there is one.

It asks what is there, never where it is

Nothing in the shell config asks “is this a work Mac?”. It asks questions it can check: does this command exist, is this function already defined. The same files then do the right thing everywhere.

If the shell finds……then this repository
Node already wrapped by a base layer (nvm, node or npm are functions)Hands Node over completely and changes nothing about it.
Suggestions-as-you-type already runningDoes not load a second copy.
Another prompt installed (pure)Switches it off cleanly before starting its own.
Another syntax highlighter loadedStands it down, so two highlighters never fight over the line.
Homebrew already set upKeeps the order the base layer chose.
A tool that is not installed (mise, fzf, starship, direnv, docker)Skips it silently. A missing tool is never an error.

The cast list in lib/

The .zshrc file itself is short. The real settings are in config/zsh/lib, one file per topic, so it is obvious where a new setting belongs.

The tmux front door

The very first thing .zshrc does is decide whether to step inside tmux. It only says yes when every one of these is true. An editor's built-in terminal, an SSH session or a script fails one of them and gets a plain shell.

Why it is fast

A shell that takes two seconds to start is two seconds you wait hundreds of times a day. Startup time is treated as a feature here, with a number attached.

Three habits get it there, and a fourth keeps it there.

  • Habit 1

    Wait until after the prompt

    Suggestions, history search and alias reminders are not needed to draw a prompt. They are loaded a moment after it appears. The alias reminder alone cost 47 ms when it loaded up front.

  • Habit 2

    Remember the answer

    Tools like Starship, fzf, mise and direnv set themselves up by printing shell code. Asking each one on every start is slow, so cached_init saves the answer and only asks again after the tool is upgraded.

  • Habit 3

    Let Tab fetch it later

    Completions for docker and orb are saved as files that zsh only opens the first time you press Tab on that command.

  • Habit 4

    Measure it, every time

    A test times real shell startups with hyperfine and fails if the fastest one is over 200 ms. A slow change cannot slip in unnoticed.

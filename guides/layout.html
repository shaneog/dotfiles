Where the files live

The real files stay in one folder, ~/.dotfiles. Your home folder holds signposts that point at them, one for each tool.

Signposts, not copies

Tools expect their settings in fixed places: git looks in ~/.config/git, SSH looks in ~/.ssh/config. Copying files there would mean two versions that drift apart. So script/setup creates symlinks instead.

In plain words

A symlink is a signpost. When git walks up to ~/.config/git it finds a sign that says “the real folder is in ~/.dotfiles/config/git”, follows it, and never notices the detour. Edit the file from either side and you are editing the same file.

The rule behind the map

script/setup names four things in the repository, and those are the only four it links.

  • Brewfile becomes a signpost named ~/.Brewfile.
  • config and ssh each become a real folder, ~/.config or ~/.ssh. Inside it goes one signpost for each thing git tracks directly inside the repository's folder.
  • claude becomes the real folder ~/.claude in the same way, one level further down. A file such as settings.json gets a signpost. A folder such as skills becomes a real folder too, and the signposts go inside it, one for each skill. Claude Code's folder says why.

Then it adds ~/.zshenv, because that one file has to sit in the home folder for zsh to find it. Nothing else at the top of the repository is on the list, so script/, test/, guides/, the Makefile and anything added later never show up in your home folder.

Why one signpost per tool

Dozens of apps keep their settings in ~/.config, and most of them have nothing to do with this repository. With one signpost per tool, their files stay in your home folder. They cannot be published by accident, and removing the dotfiles cannot delete them.

Adding a tool

Git's list of tracked files is the list of what gets linked. To bring a new tool's settings into the repository, put them under config/, git add them, and run script/setup again.

What if something is already there?

A Mac that has been used for a day already has files in these places. Setup never deletes what it finds. It picks one of four polite options.

Coming from the older layout

Earlier versions made ~/.config and ~/.ssh signposts to the repository's whole folders, so every app was writing inside the repository. On a Mac set up that way, pull the latest changes and run script/setup once. It moves everything git does not track back out into real folders at the same paths, then links one entry at a time as above.

Four files it never touches

On a managed Mac, another tool owns ~/.profile, ~/.bashrc, ~/.zprofile and ~/.zshrc, and rewrites them from time to time. Setup neither creates nor changes any of the four. They are read as a base layer instead, which Opening a terminal explains.

What git is told to ignore

Linking one entry at a time keeps most apps out of the repository, but not all of them. ~/.config/gh still is the repository's config/gh folder, so anything the GitHub CLI saves there lands inside the repository, including its record of who is logged in. Left alone, git would offer to publish it.

So .gitignore names those files one by one. The list is short, because only an app whose folder is linked can write here.

# what apps write inside a linked folder
config/gh/hosts.yml
config/tmux/plugins
config/zsh/.zcompdump

# ssh/ holds one file of ours, and everything else is turned away
ssh/*
!ssh/config

# claude/ holds what a person writes for Claude Code, and nothing it keeps for itself
claude/*
!claude/CLAUDE.md
!claude/settings.json
!claude/skills/

Good to know

Anything new under config/ shows up in git status, and a test fails until someone decides what it is: tracked, or ignored by a rule of its own. Names that should not appear in a public repository go in .git/info/exclude, which is never shared. A key copied into ssh/ by mistake is ignored, so git add passes over it. So is a copy of Claude Code's history or sign-in that ends up in claude/.

Claude Code's folder

Claude Code keeps everything in ~/.claude: the few files a person writes for it, and a great deal it writes for itself. Only the first kind belongs in a public repository.

In claude/What it is
settings.jsonClaude Code's settings on every Mac. It starts with one decision: commits and pull requests carry no “co-authored by” line and no link to the session that wrote them.
CLAUDE.mdInstructions Claude Code reads in every project, before the project's own.
skills/, agents/, commands/, rules/One entry for each skill, agent, command or rule to have on every Mac. A folder appears here when the first one is added.

Why the signposts sit one level further down

A skill written at work, for work, belongs to that Mac. If ~/.claude/skills were one signpost to the repository's folder, every skill made anywhere would land in a public repository's working folder. So ~/.claude/skills is a real folder, the repository's skills are signposts inside it, and one Mac's own skills sit beside them as real folders. Instructions for one Mac work the same way: put them in a file of their own under ~/.claude/rules/.

Why a file that is already there is left alone

Claude Code saves its own changes into settings.json, and it reads no second settings file for one Mac. A Mac that needs settings of its own therefore has to keep the real file. If setup moved it aside, it would move it aside again on every run. So in ~/.claude setup only adds. make doctor lists what a Mac has kept, as a note and not as a fault.

Good to know

On a Mac that uses the repository's settings.json, Claude Code writes through the signpost. Switch on a plugin there and git status in ~/.dotfiles shows the change. Read it before you commit it, because it can name a folder or a project, and a test refuses a path inside a home folder. git restore claude/settings.json puts it back.

A skill that should not be public

This repository is public, and not every skill should be. One that only one Mac needs can stay a real folder in ~/.claude/skills. One that several Macs need goes in a second repository, a private one, cloned by hand to ~/.dotfiles-private:

~/.dotfiles-private/
  claude/
    skills/
      a-private-skill/
        SKILL.md

Where that folder exists, setup links what it tracks under its own claude/ into ~/.claude by the same rule, after this repository's. So a name both have stays with this one, and setup says so. make update pulls the second clone before it links, and make doctor checks its signposts too. A Mac without one is missing nothing, and a Mac that cannot reach it still updates: the pull is reported as not done and the rest goes ahead.

Nothing in this repository says where the private one lives. Removing these dotfiles leaves it, and the signposts into it, alone.

Two things are deliberately not here. Claude Code keeps its list of MCP servers in ~/.claude.json, in the same file as who is signed in, so that file is never tracked. And the Claude desktop app keeps its own settings somewhere else entirely.

Three files that belong to one Mac

Some settings are different on every machine and must not be shared. Each tracked file has an untracked partner for exactly that.

Private fileAdds toWhat goes in it
~/.gitconfig-userconfig/git/configYour name, email and signing key. Required, and the only file you create yourself: by hand, or with make identity.
~/.ssh/config-localssh/configHosts only this Mac knows about. Setup creates it empty. It is read first, so it wins.
~/.zshrc.localconfig/zsh/.zshrcShell tweaks for this Mac only. Optional, and read last, so it has the final word.

Three drawers for everything else

One of the first things the shell does is name three folders. Every tool in this setup is told to use them, which keeps the home folder itself nearly empty.

  • ~/.config

    Settings

    Written by a person. The entries this repository owns are signposts into its config/ folder, tracked in git.

  • ~/.cache

    Throwaway

    Things the shell worked out once and saved to go faster, such as the completion index. Safe to delete at any time.

  • ~/.local/share

    Yours

    Data worth keeping that is not a setting: shell history, Neovim's plugins, saved tmux sessions.

Guide 7 of 7 · Staying healthy

How it stays working

Settings files do not crash when they break. A feature just quietly stops, and you find out weeks later. So this repository tests its settings the way an app tests its code.

Smoke detectors, and someone to test them

In plain words

A test is a smoke detector: it sits there quietly and shouts when something goes wrong. But a smoke detector with a flat battery is also quiet. So this repository does two things. It fits detectors everywhere, and it regularly lights a match under each one to make sure it still shouts.

Four tiers, each asking a bigger question

The quick tests run first and catch the silly mistakes. The slow ones run last and catch the subtle ones. make test runs the first three in about a minute and a half.

Nothing is tested on your real home folder

Tests that start a shell build a temporary home folder first and link the repository into it, the way script/setup would. A safety check refuses to run against anything that is not a temporary folder, so a test can never damage the files it is testing.

The tests also bring their own pretend base layer: stand-in ~/.zprofile and ~/.zshrc files that behave like a managed setup. That way the layering is tested on every Mac, with and without one, whatever that Mac really has installed.

Some tests need a Mac, and say so

Most of the tests only need a shell, so they run on Linux too. A few cannot: they ask Homebrew something, or open Ghostty, or read a file that only macOS has. Each of those carries a label, macos, with the reason written beside it.

On a Mac make test runs everything. Anywhere else it leaves the labelled tests out, tells you how many, and the rest still has to pass. So a change made on a Linux machine gets a real pass or fail, and GitHub runs the labelled tests on a Mac before the change is merged.

Why the last tier is a virtual machine

GitHub's Macs are not new Macs. Homebrew, Apple's Command Line Tools and several language managers are already on them, so a mistake that only bites a Mac with nothing installed passes every check there. make test-vm starts a copy of macOS with nothing else on it, runs the one command against the branch you are working on, checks the result and throws the machine away. It refuses an image that already has Homebrew.

It has caught two things nothing else could. One script spent two minutes of every run waiting for an answer that a Mac with no screen can never give. Another could stop forever at a “Press ENTER” prompt, and only sometimes, which GitHub never saw because its machines answer every prompt with nothing.

It needs an Apple Silicon Mac, a lot of free disk for the image, and Tart. The script checks all three before it starts and says what is missing. test/vm/run --keep leaves the machine running to look around in, and VM_IMAGE picks a different release of macOS. How long it takes has the timings from the last run.

A test has to be able to fail

Most of the real bugs in this repository hid behind a test that could not fail. It passed when the feature worked and it passed when the feature was broken, which makes it worse than no test at all. Two scripts hunt for exactly that.

  • make mutate

    Does this test still work?

    Reads a list of deliberate breakages from test/mutations.tsv. Each row names a file, how to break it, and the test that must notice. Every row is a bug that really shipped, or the failure a test was written to catch. The rows run a few at a time, each in its own copy of the repo, so one row never sees what another broke.

  • make sweep

    Is this line tested at all?

    The opposite question. It switches off each line of config in turn and reports the ones no test noticed were gone. It is slow, so it works to a time budget and picks up where it stopped.

Both want every change committed first: one tests the last commit, and the other edits files where they are and then puts them back. Both run on Linux too. There, a test that needs a Mac is reported as NOT CHECKED, never as having noticed. On GitHub the rows are checked on Linux, which is quicker, and the few whose tests need a Mac are checked on one. Once a week a Mac checks them all.

Watching the outside world

Dotfiles depend on things other people maintain: Homebrew packages, shell plugins, macOS itself. Those change without warning, so one script keeps an eye on them, and two more look at the Mac in front of you.

CommandWhat it looks for
make auditPackages that were renamed or deprecated, plugin projects that were archived, tools the config uses but the Brewfile does not install, config left behind for tools that are gone, and a Neovim lockfile nobody has updated in six months. It is about the repository, so it gives the same answer on GitHub and on any Mac.
make doctorThis Mac: its signposts, whether it is behind GitHub, the two things only you can supply, shell files another tool has rewritten, macOS settings that have drifted, and how long ago the virtual machine test last passed. Keeping a Mac up to date has the details.
make brew-driftWhat this Mac has installed that the Brewfile does not list, and the reverse. Advice only: you decide each one.

Skipping is not passing

When the audit or the doctor cannot run one of its checks, it prints NOT CHECKED and says which. Neither reports a check it skipped as a check that passed.

Robots on GitHub

Three workflows run on GitHub's disposable machines, nearly all of them Macs, so problems show up as a notification and not as a broken shell.

WorkflowWhenWhat it does
testEvery pull request, every push to main, and MondaysRuns the static, unit and integration tiers on a Mac, against both the built-in zsh and Homebrew's. A Linux machine runs every test that does not need a Mac, and the mutation list; the Mac checks the few rows that need one.
provisionMondays, or on demandRuns the install scripts for real: setup, the Brewfile, macos, remove, and bootstrap from start to finish.
auditMondays, or on demandRuns make audit.

A fourth workflow, pages, is not a test: it publishes these guides whenever a change to them reaches main.

The Macs install their tools from the same Brewfile a real Mac uses, leaving out the apps. There is no second list to keep in step.

The Monday runs matter because Homebrew packages are not pinned. A tool can change on a Tuesday, and the following Monday's run is what notices.

The shell plugins are Homebrew packages too, so the same Monday run is what notices a new release of one. tmux's plugins install at whatever is newest. The one thing with a version written down is the set of actions the workflows themselves use, and once a month Dependabot offers the newer ones in a single pull request.

The habit

Before committing a change, both of these should come back clean.

make test
make audit

And when a change claims to make something faster, the claim comes with a measurement. The startup time has a test of its own for that reason.

These guides explain. The rules for changing the repository are written once, in AGENTS.md.
